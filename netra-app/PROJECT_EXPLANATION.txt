1. PROJECT OVERVIEW
==================================================

What this project does:
NetramNova is an AI-assisted clinical retinal screening workstation designed to detect Diabetic Retinopathy (DR) from fundus (retinal) images. 

What problem it solves:
In rural India, there are millions of diabetic patients but very few ophthalmologists (retina specialists) at Primary Health Centres (PHCs). NetramNova acts as a triage system. It automatically screens patients using AI, clearing healthy patients locally and only referring high-risk (referable) patients to district hospitals. It also handles poor quality images (glare, blur) automatically before the patient leaves the clinic.

Why someone would build it:
To eliminate preventable blindness caused by Diabetic Retinopathy by multiplying specialist throughput and allowing health workers (ASHA/ANM) to easily capture gradable images on cheap/portable hardware.

Main purpose:
To bridge modern Deep Learning with Gold-Standard Clinical Practice (ETDRS 4-2-1 rules) to provide explainable and trustworthy AI diagnosis for rural telemedicine.

Main features:
- Quality Gate: Automatically rejects ungradable images (blur, glare).
- Ben Graham Adaptive Standardization: Enhances image lighting without amplifying noise.
- Sub-Pixel Patch Hunter: Detects tiny microaneurysms that standard AI misses when resizing images.
- Deterministic Clinical Guidelines: Uses a robust, static rule engine to provide gold-standard guidelines consistently.
- Edge-Deployable: Runs offline on a basic ₹10,000 laptop without requiring cloud connectivity.

Technologies used:
- Backend AI Engine: PyTorch, Torchvision, TIMM (EfficientNet-B2), OpenCV, NumPy, Flask
- Frontend Workstation: Next.js 14, React, Tailwind CSS, TypeScript
- Clinical Guidelines: Deterministic static dictionary mappings

Programming language(s):
- Python (Backend ML/CV)
- TypeScript / JavaScript (Frontend UI)

Input:
A raw fundus image captured from any retinal camera (e.g., Zeiss, Remidio, Forus 3nethra).

Processing:
1. Quality Assessment (Blur/Glare Check)
2. Image preprocessing (Ben Graham algorithm)
3. Deep Learning Classification (EfficientNet-B2)
4. Clinical Consensus Rescue Rules (e.g. searching for microaneurysms, hemorrhages)
5. Explainability overlay generation (Grad-CAM)

Output:
A localized diagnosis grade (0 to 4), confidence score, saliency heatmaps, bounding boxes for lesions, and an automated physician draft report (bilingual).

INPUT
↓
PROCESSING (Quality Gate & Ben Graham Normalization)
↓
MAIN LOGIC (EfficientNet Classifier + Clinical Rescue Engines)
↓
OUTPUT (Clinical UI with diagnosis, heatmaps, and referral decision)

3. HOW THE PROJECT STARTS
==================================================

There are two main entry points in this system (Frontend and Backend):

Frontend (Next.js Application):
1. `npm run dev` executes the start script in `package.json`.
2. Next.js server starts and loads `src/app/page.tsx`.
3. The `NetraConsoleApp` component mounts.
4. It initializes the local offline state (using `db.ts` and `MOCK_PATIENTS`).
5. The UI is displayed, showing a Dashboard of registered patients.
6. The user selects "New Scan" to begin the screening process.

Backend (Python AI Service):
1. The script `ml_pipeline/inference_service.py` runs (either as a Flask web server or via CLI).
2. The `init_model()` function is called.
3. This function loads the PyTorch `EfficientNet-B2` model weights from `best_classifier.pt` into the GPU/CPU.
4. It initializes the `GradCAM` explainer, the `ETDRSQuadrantEngine`, and the `MAPatchRescueEngine`.
5. The service listens on port 5000 for incoming images.

When the frontend sends an image, the backend runs `run_pipeline_on_image()`, which pipelines the data through quality checks, the model, and clinical rules, returning JSON back to the frontend.

==================================================
4. CORE LOGIC
==================================================

The most important part of this project is the Dual-Track AI + Clinical Consensus Architecture inside `inference_service.py`.

Standard AI models just resize the image to 512x512 and guess a number. This project does much more:

1. Quality Tri-Axis Assessment:
Before anything, it checks image Focus, Exposure (glare), and Field-of-View. If it's too blurry or overexposed, it rejects it immediately (RED ungradable), telling the health worker to retake the photo.

2. Ben Graham Adaptive Normalization:
It uses classical Computer Vision (OpenCV). It applies `4*I - 4*GaussianBlur(I) + 128` to remove uneven lighting (like a dark shadow on one side of the retina) while keeping the tiny blood vessels visible.

3. Deep Learning Classification (Track A):
The standardized image goes into an EfficientNet-B2 deep neural network. The network outputs probabilities for 5 stages of Diabetic Retinopathy (Grade 0 to 4). If the probability of Grade 2+ is above 0.40, it flags the patient as "Referable".

4. Clinical Consensus & Sub-Pixel Hunter (Track B):
Since deep learning downsamples images, it often misses tiny 10-micron microaneurysms. 
The system runs a "Sub-Pixel Patch Hunter" on the raw high-resolution image. 
Rule Engine: If the Deep Learning model says Grade 0 (Healthy), but the Patch Hunter finds an isolated microaneurysm, the system *overrules* the AI and upgrades the diagnosis to Grade 1 (Mild NPDR).

5. Deterministic Clinical Guidelines Engine:
The system uses a static, deterministic rule engine to draft the clinical report based on AIIMS/AAO guidelines, completely avoiding LLM hallucination risks while generating strict, consistent clinical and patient summaries.

6. FUNCTIONS
==================================================

Function: `init_model(ckpt_path)`
- Location: `ml_pipeline/inference_service.py`
- What it does: Loads the trained PyTorch model weights into memory.
- Parameters: `ckpt_path` (path to best_classifier.pt)
- Return value: None
- What calls it: The Flask server startup or CLI entry point.
- What it calls: PyTorch load mechanisms.
- Why it is needed: Loading a model takes time. Doing it once at startup allows subsequent image predictions to happen in milliseconds.

Function: `run_pipeline_on_image(image_bytes, image_path)`
- Location: `ml_pipeline/inference_service.py`
- What it does: The master function that orchestrates the entire AI diagnostic process.
- Parameters: Raw image bytes or a file path.
- Return value: A JSON dictionary containing the diagnosis, quality metrics, and explainability data.
- What calls it: The Flask HTTP POST endpoint when the frontend uploads a scan.
- What it calls: `check_quality`, `full_pipeline`, `MODEL()`, ETDRS Rule Engines.
- Why it is needed: It ties together all the disparate CV, DL, and Rule engines into one pipeline.

7. CLASSES / OBJECTS

Class: `EfficientNetDRClassifier`

Class: `MAPatchRescueEngine`
- Purpose: A classical computer vision rule engine.
- Methods: Methods to scan the green channel of the high-res image for microaneurysms.
- Why it exists: Neural networks downsample images to 512x512, which destroys 10-pixel microaneurysms. This class operates on the raw image to "rescue" false negatives.

==================================================
11. ERROR HANDLING
==================================================

- Quality Rejection: If the image is blurry, `check_quality()` returns `{passed: False}`. The backend safely aborts deep learning inference and returns an error explaining to the user exactly why (e.g., "Flash glare detected. Adjust angle.").
- Decoding Errors: If a corrupt image is uploaded, OpenCV returns `None`, and the backend gracefully returns `{"error": "Could not decode fundus image file"}`.
- Offline Fallback: The frontend Next.js app uses local state and `db.json` to store patient data if the internet is down, syncing later when connection restores.
- Deterministic Safety: By using a hardcoded, deterministic clinical guideline engine mapped directly from AIIMS/AAO guidelines, the system fundamentally eliminates any risk of LLM hallucinations.

==================================================
12. SECURITY
==================================================

- Offline Data Privacy: Rural internet is unreliable. By processing inference locally (edge AI) and storing patient data in local IndexedDB/db.json, patient health data (PHI) never leaves the clinic unless explicitly synced to the district hospital.
- Read-Only Validation: The Next.js backend uses strict TypeScript typing to ensure database schemas are not corrupted.
- Deterministic Safety: Instead of using unpredictable LLMs, the system relies on static, reviewed clinical guidelines mapping, ensuring 100% safe, non-hallucinated medical advice.

15. CODE-POINTING QUESTIONS
==================================================

Professor: "What does `init_model()` do in `inference_service.py`?"
Answer: It loads the PyTorch EfficientNet-B2 weights into memory and initializes the Grad-CAM explainer. It only runs once so that subsequent requests don't suffer loading latency.

Professor: "Why are you checking `if raw_pred == 2 and p_ref >= 0.65`?"
Answer: This is the clinical rescue logic. If the AI is fairly confident the patient has Grade 2 DR, we trigger the ETDRS Rule 4 engine to count hemorrhages. If there are enough, we override the AI and upgrade them to Grade 3 (Severe NPDR).

Professor: "Why is `db.ts` checking for `/tmp/db.json`?"
Answer: When deployed on Vercel, the main filesystem is read-only. We check for the Vercel environment and write our mock database to the `/tmp/` directory so the app can still function.

Professor: "Why use `albumentations` instead of standard torchvision transforms?"
Answer: Albumentations is significantly faster and handles bounding box transformations automatically, which is vital when training object detection models or manipulating images rapidly for inference.

16. WHY THIS TECHNOLOGY?
==================================================

PyTorch:
- What: A deep learning framework by Meta.
- Why: It offers dynamic computation graphs, making it much easier to implement custom clinical rule logic alongside the neural network than TensorFlow.
- Alternative: TensorFlow / Keras.

Next.js:
- What: A React framework for building full-stack web applications.
- Why: Provides excellent routing, API endpoints, and fast rendering, making it easy to build a complex clinical dashboard quickly.
- Alternative: Plain React with Express.js, or Angular.

EfficientNet:
- What: A family of highly optimized convolutional neural networks.
- Why: Scales depth, width, and resolution efficiently. B2 provides the perfect balance of accuracy and edge-device (CPU) performance.
- Alternative: ResNet-50 (too heavy), MobileNet (too inaccurate).

Deterministic Guidelines Engine:
- What: A static dictionary mapping of grades to AIIMS/AAO guidelines.
- Why: To create a verifiable, 100% safe clinical report completely immune to LLM hallucinations.
- Alternative: LLM-based RAG (removed for safety concerns).

==================================================
17. LIMITATIONS
==================================================

- Mock Database: The current implementation uses a local JSON file (`db.json`) instead of a robust relational database like PostgreSQL, meaning it cannot handle concurrent writes well at scale.
- Cataract Interference: Severe cataracts block the retina. The AI might confuse this blurriness for an ungradable image or misinterpret scatter as exudates.
- Hardware Constraint: While optimized for CPU, processing the 512x512 image through EfficientNet and running Patch Hunters still takes ~100-200ms on a CPU, which is fast, but real-time video streaming analysis would require a GPU.
